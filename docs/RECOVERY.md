# 持久作业恢复

`reconciliation.ReconciliationService` 将只读 Slurm 查询接入账本。它只接收已有请求编号，从已保存的提交意图取出请求身份、清单摘要和 UTC 查询起点；不接受生成 Agent 提供的最终费用、作业归属或查询时间范围。查询前保存单次票据，查询后在一个 SQLite 事务中完成作业绑定、状态记录及最终核时入账。

## 使用入口

这是受信管理员的一次恢复操作，不是后台守护服务，也不是主 Agent 的任意 SSH 工具：

```sh
python3 -m auto_lammps.worker \
  --ledger "$HOME/.local/share/auto-lammps-private/execution.sqlite" \
  --ssh-alias APPROVED_LOGIN_ALIAS \
  --audit-directory "$HOME/.local/share/auto-lammps-private/scheduler-receipts"
```

必须已有本项目的私人账本；文件名拼错时不会新建空账本冒充恢复成功。别名使用管理员已批准的实际配置；命令不配置凭据、不创建评测、不提交也不取消作业。可以加 `--request-id` 明确刷新一个已有派发请求。参数和输出属于本机私人运行信息，不得贴入公有日志。

默认恢复未解决的已派发请求，以及已经调度结束但尚未完成核时记账的请求。已经准备但未派发的请求不会执行。已完成且核时已确认的作业默认不再轮询；需要复核时按请求编号显式查询。没有自动定时或离线唤醒承诺。

## 一致性规则

- 每次查询使用持久票据。较新的查询或取消/状态事件使旧响应失效；旧响应仍留档，不能覆盖较新结果。
- 同票据、同回执可重复写入但只生效一次；同票据换回执会被拒绝。不同查询取得相同最终费用时保留各自来源，不重复计算成本。
- 找不到作业、查询失败或信息不完整时保留费用与提交机会。成功接受但回执丢失时，通过精确请求身份重新绑定作业，不重提。
- 作业身份变化、终态变化、重复分配、重新排队或已确认费用变化会保留历史并进入 `reconcile_required`。该批次新预留及已准备请求的派发都停止。取消意图不能解除这个状态；自动解决重排队与管理员冲突处置接口尚未实现。
- 接受、终态与核算在一个事务内记录。任何一步写入失败会整体回滚；旧版路径留下的“终态但尚未核算”也包含在恢复列表。
- 实际核时超额照实保存，不截断成批准额度。原始证据摘要可追溯至仓库之外的只读查询回执。
- 调度完成不等于输出完整或科学通过；本模块不进行评分，不向主 Agent 暴露目标答案。

## 验证与边界

测试使用合成调度数据：覆盖跨进程同票据竞争、账本重新打开、回执丢失、从原始调度文本到私人回执再到最终核算、旧响应、取消、超支、冲突阻断、审计事务失败回滚，以及管理员入口。没有目标能量/力/动力学计算，也没有模型调用。

上一阶段在批准入口的真实空查询仅证明连接与参数兼容。本阶段没有提交真实作业；不能将上述合成恢复测试称为真实 HPC 作业恢复验收。生产上传、受审脚本提交、远程存储控制、真实取消、运行输出取回、系统权限隔离与科学检查仍待完成。
