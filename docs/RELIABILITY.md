# 失败经验如何进入产品

这是产品设计与待验收清单，不代表下列能力已经全部实现。关联 Issue #71；事件事实见
[项目审计](AUDIT.md)。近期执行优先级仍为已有引擎上的原作者参考 A，不能把建设完整知识库
变成首次计算的新门槛。

## 职责

Agent 根据任务和证据提出方案；RAG 检索适用的知识与经验；领域 Adapter 将方案转成
受约束、可检查、可恢复的工具操作。服务端账本执行预算、计数与状态规则。
检索命中只是带来源的候选依据，不能代替执行结果或科学核验。

三次真实参考提交新增的经验：Slurm 字段解析须容纳带空格的命令值并防重复身份覆盖；
登录节点与计算节点的辅助程序证据不能互换；原生 Slurm 的 MPI 启动方式不能沿用为隔离
帮助查询设置的强制 fork。第一个修复已有后续分配解析证据，后两个不能标为已完成运行
验收。经验索引须保存这种逐项状态，不能将整个故障单统一提升为“已验证”。

| 可能重现的问题 | Adapter 应落实的机制 | RAG 应提供的依据 | 验收反例 |
|---|---|---|---|
| 已有软件却重新下载、编译；重复检查 | 按程序摘要、环境及依赖记录能力；复用未失效的证据，只刷新变化部分；构建必须有具体缺失理由 | 软件版本说明、已验证配置、历史错误的适用环境和已证实修复 | 一个模块缺 MEAM、另一个已支持时，选用现有合适模块；不触发编译 |
| 错误晶体、成分、晶向或边界 | 结构生成前后核对任务约束、晶胞、元素计数、坐标变换和边界；几何检查与物理稳定性检查分开 | 有来源的晶体描述、建模方法、支持材料范围及失败案例 | 非立方晶胞、晶向变换或元素顺序错误被发现；不能自动换成方便的立方结构 |
| 势函数存在但不适用，或元素映射错误 | 校验文件身份、单位、原子类型映射、必需软件包；检查任务所需适用证据 | 势函数原始来源、版本、材料与性质验证范围；公开不等于科学适用 | 同元素但不同结构/工况的模型不能只靠名称匹配获准；索引互换必须报错 |
| 作业返回不明后重复提交 | 提交前记账、唯一派发身份、断线后先对账，恢复已有任务 | 调度器诊断及具体环境下的恢复方法 | 接受提交后断线、后台重启仍仅产生一个真实作业，次数不重置 |
| 数据列、单位、应力定义或体积归一化错误 | 用版本化解析器保留原始输出；验证任务身份、完整性、阶段、列、单位与转换；按预定计划分析 | 格式说明、物理量定义、分析方法与已核验转换；保留来源及适用条件 | 截断轨迹、旧任务日志、压力/应力符号或体积定义混淆不能生成“成功”报告 |
| 相同错误不断重试，或通过改任务得到成功 | 记录失败类型、动作及结果；相同状态不重复同一无效动作；修复不改冻结科学条件、不绕过两次提交限制 | 已验证的失败—原因—修复案例；未验证推测另列 | 失败后不得缩小体系、缩短采样、更换模型或改变评分来冒充原任务成功 |

## 检索与证据的有效性

知识条目至少包含：来源及定位、版本/摘要、适用材料和任务、环境与工具版本、观察到的
错误、诊断、采取的动作、验证证据、验证状态、失败反例、访问范围及更新时间。
候选修复与经验证修复分开，保留过时、撤回及相互矛盾的记录。

检索先按访问权限和任务允许资源过滤，再按元素、结构、性质、方法和软件条件匹配，
最后排序；语义相似度不能覆盖这些约束。答案须能追溯到实际使用的条目。
找不到适用证据时返回明确缺项，不编造参数；来源冲突时保留冲突，不能静默挑选。
外部论文、仓库与日志中的指令视为数据，不能改变权限、预算或工作流。

环境能力记录绑定实际程序和依赖身份。身份、集群配置或相关输入改变，或出现与旧证据
矛盾的真实错误，才使对应证据需要刷新。过期策略按证据类型定义，不能把每次思考都当成
从零审计。帮助输出证明功能声明，实际计算证明可执行，科学核验另行记录。

## 评测隔离与受控改进

参考库保存 P、A 和作者解法；被测 Agent 的检索库只包含允许输入、通用知识及获准的
开发集经验。权限在检索、文件和工具层执行，不能只靠提示词。当前测试的目标源码、
答案、专用后处理及带答案的错误日志不得通过 RAG 泄露给 B。

开发失败先记录事实，提出原因假设，再通过修复和复验确认。确认后的通用经验可进入
下一版本的知识库；工具代码、检索规则与知识发布保留版本、审查和回退记录。
任务运行期间固定版本，正式测试结果不在同一测试内用于更新知识、修改评分或提示第二次
尝试。用某个测试失败改进后，该任务对新版本属于开发案例。

## 当前实现与接入顺序

已有结构准备、势函数静态校验、输入快照、持久账本、恢复、输出回收及冻结数值分析模块；
各自验证范围见相应规范。尚未完成统一能力目录、领域知识检索、失败经验检索及其权限
验收，也未证明这些机制能在真实科研任务中降低失败率。

1. 第一周沿现有接口完成 A、再按批准策略推进 B；记录实际错误和人工介入，不再重写框架。
2. 第二周接入独立 API 时，在同一候选流程接入能力目录与有来源的检索，先覆盖首个真实
   任务所需结构、势函数和输出方法，再从开发失败形成一项可复验的修复。
3. 使用相同模型、任务、允许资源和预算比较改进前后首次成功率、两次内成功率、科学
   误差、人工介入和成本。分别关闭检索或领域规则时保留预算、安全及计数约束；未做比较
   前不宣称某个组件提高了成功率，也不凭一篇任务宣称达到普遍 90%。

网页展示“已找到可用环境”“结构检查未通过：元素数量与要求不同”“输出缺少后半段”等
具体状态，并可展开来源、处理历史和剩余提交次数。普通用户不需要配置检索索引或解释
底层错误；仅当科学条件缺失、冲突或资源授权不足时集中询问。
