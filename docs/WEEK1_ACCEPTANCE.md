# 第一周 P-A-B 流程验证

本文件落实原始三周规范及用户对自动化边界的澄清，关联 Issue #15。它是验收要求，不代表下述能力已经实现；当前证据见 [逐项核对](WEEK1_AUDIT.md)。

## 交付目标

最终产品是自然语言科研计算服务，正常用户不必提供论文。本文件描述第一周使用文献任务测试产品的验收路径；测试需求必须进入产品本身的同一主 Agent、领域 Adapter 和计算分析流程。不得用只为论文编写的独立演示链路替代产品验收。

研究者在网页选择或提供一篇真实论文，用自然语言指定研究需求。软件自动整理证据、建立作者参考结果、生成不含答案的任务、驱动主 Agent 独立准备并执行计算，最终呈现可追溯的科学比较和文件。

首篇须事先确认能支撑论文核心结论的完整计算任务或任务集合，逐项列出图、表、物理量和条件。部分复现明确标注范围；不能用孤立数值点替代约定任务，也不能凭一篇开发论文宣称达到普遍 90% 成功率。

## 人与软件的分工

| 环节 | 软件负责 | 研究者参与 |
|---|---|---|
| 输入与证据 | 读取授权论文、补充材料及关联代码，整理条件、目标和出处；输入与评分资料分离 | 提供或选定论文，描述需求 |
| 范围与条件 | 自动生成可读的任务摘要；区分已找到、相互冲突、缺失和系统建议的条件 | 确认范围、条件摘要和事先确定的判据；只补充软件确实无法取得的科学信息 |
| 参考运行 | 固定作者代码、模型、数据和环境；准备、提交、监控、回收并核验 A 对 P | 处理无法自动解决且会改变科学条件的决定；所有介入留痕 |
| 主 Agent | 读取允许资源，自主生成结构、势函数调用、目标脚本和分析方案；静态检查、冻结、提交、回收和一次修复 | 正式评测中不替 Agent 改方案、脚本或提示答案 |
| 分析与结果 | 按冻结方法分析并独立比较 P、A、B；生成图表、文件及来源链 | 查看结果、追溯证据、导出资料 |

条件确认可以集中完成，底层仍保存逐字段来源及确认记录。不能要求用户为了推进流程逐项抄写已在资料中的参数、选择内部文件映射、操作终端或手工串联阶段。条件不能确定时，软件指出具体缺项及依据；自动化不意味着默许未知参数。

用户最新明确阶段分工：**第一周由 Codex 负责真实 P-A-B 流程的准备、执行编排、分析和验证；第二周开始接入独立运行 API。**第一周不是只做离线联调，也不因尚未配置 API 而停止真实流程准备。首次验证跑通后再向用户索取 API 配置，供第二周使用。

第一周记录 Codex 参与的步骤与实际工具执行证据；流程跑通不等于已经证明独立 API 的自动化能力。第二周由独立 API 接管需要模型决策的阶段，复用相同产品接口和记录体系，再验证自动化。进入 B 前必须先报告策略并获得用户确认；已见过参考资料的开发上下文不能自称盲测，需在策略中明确 B 的输入与访问隔离安排。现有 HPC、计次、预算和科学条件要求保持有效。

## 必须实际通过的路径

1. 从论文及自然语言生成带出处的条件和结果条目；条目级核实 LAMMPS 来源，不能按整篇标签推定。
2. 明确范围、评分规则与预算，集中确认科学条件；固定所需势函数、输入数据和软件版本。
3. 参考端通过记账入口执行作者工作流，取得本次真实 A 并核验 A 对 P。作者归档日志不能代替这次运行。
4. 导出允许输入任务包与独立参考评分资料，并核验实际访问隔离。主端不能通过源论文、目标仓库或日志取回答案。
5. 第一周由 Codex 负责组织 B 的生成与工作流冻结，具体隔离策略须先获用户确认；第二周转为独立运行 API 驱动。所有目标物理计算只在批准 HPC 计算节点、经受控入口执行。
6. 自动监控、回收、检查输出，必要时仅基于可见错误进行一次集中修复。每次正式评测最多两次真实提交请求，含拒绝和状态不明事件；不得重命名重置次数或在作业内隐藏试错。
7. 自动分析、绘图与独立评分。分别判断计算结束、输出有效、科学通过；按任务需要接入成熟分析工具和 OVITO。
8. 网页显示真实阶段、提交次数、费用用量和完整历史，提供结果比较及资料导出；刷新或服务恢复不能重复提交。

每一步都需要对应的运行记录、版本、输入输出和状态证据。模拟服务的测试只能证明软件逻辑。参考端人工干预、主端人工干预和开发修改分别记录，不能删除失败或把人工辅助运行标为无人修改成功。

## 当前缺口与实施顺序

目前已具备文献发现、条件草稿、提交账本、执行适配器和历史页面的基础；尚未完成以上整条路径。继续人工筛选候选或增加表单，不足以补齐自动化缺口。

接下来的代码工作应依次贯通：

1. **条件整理与模型接口**：第一周由 Codex 负责整理和验证，保留来源与工具记录；独立提供方、模型、密钥及调用预算在第二周配置并验证。复用 `literature.py`、`tasks.py` 的来源与冻结机制，让软件生成条件摘要及具体问题，减少手工录入。
2. **首篇参考准备与双份资料**：完成首篇资源核验和范围确认，把提取、资源获取、任务包分离及作者参考工作流准备接入应用；人工核对作为验收手段保留。
3. **应用执行链路**：在现有 `worker.py`、提交与恢复接口之上连接独立生成、计数、实际 HPC、取回与一次修复；不另建通用框架。
4. **分析、评分与结果页**：围绕约定图表和物理量实现分析、P-A-B 判断、真实进度、导出和完整历史；条件输入页同步改为摘要确认与例外处理。

接口、解析及无付费模拟测试可以先开发；真实模型调用需要提供方配置和获批预算。真实 HPC 执行还需明确范围、判据、已审查版本及部署验收。已有授权持续有效，不重复请求。

第二周先接入真实 API，验证同一流程的自动化，再推进跨任务重复评测、基线和一次可审查的系统改进；第三周扩大覆盖并冻结正式评测。历史讨论中的较早数量建议不替代最终三周规范，也不把第二、三周任务移入第一周成功声明。

## 首次 P-A-B 跑通后的用户界面验收

用户明确指出当前逐项条件表单与字段映射页面无法供普通研究者正确完成任务。首次真实 P-A-B 验证跑通后，必须重做主要操作流程，而不只是调整配色。

- 两个入口：描述研究需求；验证一篇论文。普通科研无需论文；文献验证可选 Zotero 条目或提供文章。
- 默认只要求用户给出自然语言需求及其已有资料；由软件完成证据整理、结构与势函数准备、计算和分析的阶段衔接。
- 已有资料能回答的条件由软件提取；仅在影响科学含义的缺项或冲突处集中提问，不要求用户逐字段搬运证据、选择内部映射或配置任务包。
- 正常页面显示当前工作、等待原因、用户必要操作、结果及其可靠性、提交次数、预算和完整历史。脚本、字段与技术日志按需展开。
- 验收必须从空白页面走通两类用户任务；不能靠开发者在后台补数据库、拼接步骤或代填内部字段后宣称人类可用。第一周 Codex 科学执行参与另记，不替代界面使用验收；第二周以真实 API 验证自动衔接。

当前页面仍是开发辅助界面，不能声称已经满足此项验收。
