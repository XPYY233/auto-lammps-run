# 用户端操作观察

2026-09-30，Issue #153；沿用户指定既有任务进行，开发诊断不计为用户操作通过。

| 页面 | 观察 | 对用户的影响 | 后续处理 |
|---|---|---|---|
| 我的任务 | 详情按钮点击无变化，键盘 Enter 可用 | 无法判断是否接收操作 | 复查真实点击与加载反馈 |
| 任务详情 | 待准备任务先展示空结果，条件/准备藏在折叠项内 | 不知道下一步在哪里 | 把当前必需动作前置 |
| 任务详情 | 模型已配置但侧栏称“应用模型尚未启用” | 误以为需重复设置密钥 | 根据实时服务状态展示 |
| 任务引导 | 示例建议“只做最小超胞先验证” | 容易无意缩小用户科研目标 | 改为保持范围的澄清示例 |

- 已有任务把用户并列要求的三种超胞误作三个冲突值；自然语言物理量名称与等价公式也误报冲突。恢复时通过页面补充完整条件并记下选择依据，保留原证据。提取提示已明确扫描列表合并；等价判定与批量确认仍待优化。
- 用户要完成普通任务，需分别确认 19 项，其中静态计算的时间步长、系综等也需逐个填“不适用”；这一负担应由应用模型集中给出建议并一次审阅。

当前阶段核心：按照用户最新要求，优先完善系统架构中的完整执行流程。界面只优先修复阻塞操作或掩盖状态的问题；不以视觉改版代替自动化验收。

- 冻结后的按钮叫“开始自动计算”，下方却同时写“自动准备、提交与分析”和“这里只准备不提交”，批准关卡语义不清。应按当前阶段显示“生成计算方案”→“批准并提交”→运行/分析。
- 条件确认后仍展开全部历史候选，旧错误建议与当前已选条件并排，且来源仍写“待确认”；应以当前选择为主卡片，原始候选归入历史展开。
- 模型响应被输出长度上限截断时，页面只显示 incomplete_generation；应解释为“方案未完整生成”，同时显示系统是否能自动恢复。
- 人工方案确认不应要求用户理解脚本。应用须在准备阶段自动建立需求与步骤/数据的对应，页面展示摘要、预期产物和资源，技术文件放到可选详情。

- 完整方案的思考生成与语义审核每轮可能持续数分钟，当前页面只有阶段名；需显示开始时间、已耗时、是否仍有后台请求，且不能把等待推断为失败或自动重复调用。后续将确定性技术规则交给适配器，模型侧保留科研需求一致性判断，并分别统计首次方案通过率、自动修复次数及耗时。

- 2026-09-30：用户把“作业+准备ID”理解为HPC提交成功。必须严格区分方案记录、提交申请与调度器Job ID；任务右栏直接显示真实作业号和调度状态，尚未提交/未知回执也明确可见。已修正文案与状态呈现，真实调度仍待用户流程验证。

- 2026-09-30：用户看到完整脚本但长期停在方案准备，合理怀疑适配器未接入。需要显示可理解的阻塞原因及自动修复进展；确定性格式应由编译器处理，不应让研究者排查语法，也不能把静态审核误报作为科研不足。已接入几何/势函数/脚本展开不等于端到端执行成熟。

## 下一阶段：方案工作区（用户明确要求，2026-09-30）

当前优先完成原任务经应用实际提交及执行；以下界面整改随后集中完成，不以改版代替主线。

1. 页面前置当前方案卡：研究目标、步骤、产物、资源及方案版本；脚本/结构是可展开详情，不能要求用户从“研究条件”中寻找。
2. 当前方案旁提供“要求修改”输入与动作；保留同一方案的迭代链，显示本次修改内容、修改原因与上一版差异。
3. 明确区分“正在修改”“修改完成、等待确认”“存在问题”，修复后自动更新当前版本，不能继续展示旧方案而无提示。
4. 提供清楚的“批准并提交”动作；批准绑定当前方案，方案变化后旧批准失效。用户应审阅研究摘要与资源，不承担代码查错工作。
5. 批准后持续显示提交申请、HPC已接收（真实作业号）、排队、运行或失败；失败给出原因与可行下一步；未知回执不得显示成功或重提。
6. AI状态直接可见：当前步骤、正在做的事、已完成的检查/产物、阻塞原因、开始时间/耗时、自动修复轮次与下一步。关闭浏览器后后台继续，重新打开可恢复同一状态。

验收：不熟悉项目的研究者能在一个页面找到方案→提出修改→辨认新版本→批准→核对真实HPC回执，全程无需看开发者日志或询问操作位置。对实时AI状态的展示必须来自已记录事件，不伪造百分比或完成情况。
